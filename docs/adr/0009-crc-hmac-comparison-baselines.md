# CRC and keyed HMAC are comparison baselines for the tagging scheme: CRC against random errors only, end-to-end HMAC against random errors and the intelligent attacker

The orthogonal self-tag (`check_orth_packet`, `<p,p> == 0`) is the project's own integrity mechanism. To position it in the thesis we add two standard, non-homomorphic baselines — a keyless checksum (CRC) and a keyed MAC (HMAC) — and compare them to the orthogonal tag on **detection/recovery outcome, transmission overhead, and computation**. This ADR fixes which baseline is tested against which threat, the trust model each operates under, and the tag widths, so the numbers in the results chapter have a fixed reference.

**The decisive fact: CRC and HMAC do not survive RLNC recoding; the orthogonal tag does.** A recoded packet `p = Σ cᵢ pᵢ` (with `cᵢ ∈ GF(2^m)`) is still self-orthogonal for free, because the generation is mutually and self-orthogonal and the inner product is bilinear — so the orthogonal tag is effectively homomorphic under recoding. A source-computed CRC is linear only over GF(2), not under GF(2^m) scalar multiplication, and an HMAC is not linear at all; both are invalid the instant a relay recodes. Every decision below follows from this.

**Where each baseline is tested (settled).**
- **CRC — random-error recovery sim only** (`simulation/recovery_decode_sim.py` regime). This sim is **single-hop**: the source recodes each round, a BER channel corrupts the packet, the receiver checks. There is no relay between tagging and checking, so a source-computed CRC over each recoded packet verifies cleanly — no recoding problem. CRC is the natural keyless baseline for *random* corruption. It is **not** tested against the intelligent attacker, where it is trivially defeated (a white-box forger recomputes the CRC).
- **HMAC — both the random-error recovery sim and the intelligent-attack sim** (`simulation/intelligent_attack_sim.py`), as the security baseline.

**HMAC trust model: end-to-end, source–receiver key, relay only forwards (minimum scope, chosen).** In the attack sim the malicious relay forwards-and-records honest packets and injects forged ones; it does **not** recode. HMAC uses a key shared source↔receiver that the relay does not hold. Honest packets are source-signed and forwarded intact, so they verify; forged packets cannot be signed without the key, so they are rejected outright. Expected result: **HMAC drives the silent-accept rate to 0 — it defeats the targeted forgery completely.** The honest caveat, stated explicitly in the thesis: this holds *only because relays do not recode*; end-to-end HMAC is incompatible with in-network recoding, which is exactly the capability the orthogonal tag preserves.

**Deferred extension (noted for supervisors): per-hop HMAC with a recoding, insider relay.** If relays recode, each must re-sign, so the key lives at every relay — and a malicious relay then holds it and signs its own forgery with a valid MAC. HMAC would provide **zero** protection (the classic "MACs do not secure network coding against Byzantine insiders" result that motivates homomorphic MACs/signatures). This is the more interesting head-to-head but requires giving the relay a recoding step the current sim lacks. Implement only if supervisors want the head-to-head numbers.

**Capability model: each scheme runs at its natural capability (chosen; no leveling).** The orthogonal scheme keeps its full three-stage machine — self-check → cross-verify trust gate `V` → **in-place bit-flip repair**. CRC and HMAC are detection-only (not error-correcting), so their mode is **check → drop the bad packet → let RLNC's send-until-decodable redundancy pull a replacement**. The thesis advantage this is designed to expose: *because the orthogonal scheme repairs instead of dropping, it reaches a decodable basis in fewer transmissions.* The comparison is on where the arms end up — decode-success, silent-decode, overhead (transmissions), computation — not on a leveled detect-and-drop control.

**The false-accept contrast that drives the results table.** Under random BER a corrupted packet passes CRC-32 or HMAC with probability ≈ `2^-width` (2^−32, 2^−128) in **one shot** — a MAC *is* the trust, no cross-verify needed. The orthogonal self-check false-accepts at ≈ `2^-m` (2^−8 for GF(2⁸)) — the silent-decode source — and needs `V` cross-checks to reach ≈ `2^-mV`. So the orthogonal tag buys recoding-survival and in-place repair at the price of a weaker single-shot check that must be shored up with cross-verification.

**Tag widths and overhead accounting (settled).**
- **Orthogonal tag:** `gen_size` symbols per packet = `gen_size · m` bits. **Grows with generation size** (10 bytes at gen_size=10, m=8). This is a genuine per-packet disadvantage, offset by fewer transmissions.
- **CRC:** CRC-32 (`zlib.crc32`), 32 bits = 4 bytes, keyless, fixed.
- **HMAC:** HMAC-SHA-256 (`hmac` + `hashlib`), **truncated to 128 bits (16 bytes)** as the primary. Optionally also report full 256-bit and a light 64-bit variant to draw the overhead/security curve.
- **Overhead unit:** tag-block bits (or bytes) **per packet**, excluding the coefficient and data blocks (common to all three). Report absolute and as a ratio to payload, and include **at least one gen_size sweep** so the orthogonal tag's linear growth is visible against the flat CRC/HMAC lines.

**Computation currency (settled): native per-scheme op counts + asymptotic complexity, reported at two levels; no forced common unit.** The three verifications are incommensurable primitives (field-muls vs byte table-lookups vs SHA block-compressions), so we count each scheme's dominant primitive in its own unit and report both **per-verification** cost and **cumulative-per-trial** cost (the latter charges the orthogonal scheme for its repair search and CRC/HMAC for the retransmissions they trigger). We report constants, not just O(·), because fixed costs dominate at our small packet sizes. **Wall-clock is a labeled secondary only**, unfair as a headline because the orthogonal tag is pure-Python while CRC/HMAC call optimized C stdlib — see [`docs/comparison_methodology_notes.md`](../comparison_methodology_notes.md) for the full list of confounds (implementation-level, SHA-NI hardware acceleration, per-packet vs system cost) prepared for the supervisor discussion.

**Code structure (settled): a pluggable `IntegrityScheme` interface + a parallel comparison driver; the validated sims stay untouched.** Both existing loops reduce to build-source → per round (recode → attach tag → pollute → append → admit → `_try_decode`), where only *attach* and *admit* differ per scheme. The interface: `make_source` (orthogonal builds the tag block, CRC/HMAC use plain data + a ground-truth suffix), `attach(instrument, packet)` (orthogonal ≈ no-op — the tag rides along homomorphically; CRC/HMAC append a MAC over `[coeffs|data]`), `admit(instrument, pool, gen_size, …)` → accepted code-packets (orthogonal = `recover_generation_bitflip` + `_accepted_packets`; CRC/HMAC = verify → drop → strip tag), `tag_overhead_bits(gen_size, m)`, and `new_instrument(field)` (its native op counter — `CountingField` for orthogonal, a byte-lookup counter for CRC, a block-compression counter for HMAC). `_try_decode` is shared and unchanged.

We do **not** refactor `recovery_decode_sim.py` or `intelligent_attack_sim.py` — they *are* the validated orthogonal baseline (the V=2 / silent-decode findings), so editing them risks silently shifting those numbers. Instead: new `simulation/integrity_schemes.py` (the three schemes; `OrthogonalScheme` calls the same `recover_generation_bitflip` / `_accepted_packets`, so it reproduces the standalone sim as a free cross-check) and a generic `simulation/scheme_comparison_sim.py` driver that sweeps BER (all three schemes) and strike-S (orthogonal vs HMAC), emitting overhead + op-count + outcome tables. New files only.
